# ADR 0001: シミュレーションを Three.js から独立した純 TypeScript 層に置く

## 背景

この作品の面白さは振り子・慣性・落下感の 3 点にある。つまり**物理そのものが製品**であり、そこが壊れていれば見た目が整っていても失敗する。

一方で Three.js の描画層はブラウザの WebGL に依存し、jsdom では意味のあるテストが書けない。物理を描画層に埋め込むと、製品の中心部分が「動かしてみないと分からない」領域に入ってしまう。

## 決定

`src/engine/` を純 TypeScript の層として切り出し、次を禁止する。

- `three` の import
- DOM API（`window` / `document` / `requestAnimationFrame` / `performance.now` / `Date.now`）
- `Math.random`

時間は必ず引数の `dt` として受け取る。都市はセル座標のハッシュから決定論的に導出し、状態も乱数シードも持たない。ベクトル演算は `three` の `Vector3` ではなく自前の不変な `Vec3` を使う。

描画層は engine の関数を**呼ぶだけ**で、物理を再実装しない。

カバレッジ 80% のゲートはこの層（と `src/lib` / `src/hooks`）にだけ掛ける。

## 捨てた案

- **Three.js のオブジェクトをそのまま状態に使う**: 実装は短くなるが、物理の検証にブラウザが要る。振り子のエネルギー保存やフレームレート非依存性は、数値で確かめないと「なんとなく動いている」以上のことが言えない。
- **描画層に薄い物理を書き、テストは E2E に寄せる**: E2E は遅く、失敗したときに原因の切り分けができない。実際、開発中に見つかった欠陥（高リフレッシュレートでの停止、ray の距離が方向ベクトル長に依存する等）は、いずれも単体テストで赤にできる形だった。

## 変えてよい前提 / 壊すと危ない前提

- **変えてよい**: `tuning.ts` の数値すべて（重力・空気抵抗・巻き取り速度・街の寸法・カメラの時定数・FOV のゲイン）。engine のテストは挙動の性質を見ており、特定の数値に依存していない
- **変えてよい**: `Vec3` の実装（不変であれば内部表現は自由）
- **壊すと危ない**: engine から `three` / DOM / 乱数への依存を持ち込むこと。1 箇所でも入れば、この層をテストできる根拠が消える
- **壊すと危ない**: 描画層で物理を再実装すること。テスト済みの挙動と画面の挙動が黙ってずれる
- **壊すと危ない**: `advanceSwinger` が `dt` 以外から時刻を取ること。テストが実時計に依存し、再現しなくなる
